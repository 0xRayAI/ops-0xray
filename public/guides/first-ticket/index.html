First ticket

Run your first agent ticket end to end

Yes. One ticket can go from assigned to shipped in an afternoon. Point the builder's station card at the ticket, build on a branch, get a reviewer PASS, run npx @0xray/foundry gate, and post the receipt. Then close the session mid-ticket on purpose and confirm a fresh one resumes the same work.

Is your team stood up first?

This guide starts where Stand up an agent team ends: roles named, house rules on disk, kit fastened with a PASS, one queue open, and a first ticket filed with an owner, a stage, and a state. If any of that is missing, do stand-up first. Here we run that ticket through the loop.

How do you point the station card at the ticket?

The station card (.xray/state/STATION.md) is the compact live ticket for a seat: what it is doing, which branch, which pull request, what is next. The suit's hot-swap rule is plain: read the station card before other work, and continue the card instead of restarting the job.

Write the builder's card by hand the first time: ticket link, branch name, next step. After that the seat updates it at the end of every session.

A good card fits on one screen. Something like:

ticket: #42 add the retry note to the deploy doc
branch: builder/42-retry-note
pr: #57 (open, waiting on review)
last: drafted section, ran local checks
next: answer reviewer FIX on wording, re-request review
blocked: none

If a line would take a paragraph, it belongs on the ticket, not the card. The card is a pointer, not a diary. Keep the reviewer's card just as short: which pull request, which verdict, what it is waiting on.

How does the ticket move from build to ship?

  1. Coordinator assigns the ticket to the builder.
  2. Builder creates a branch and worktree, makes the change, opens a pull request, updates its station card.
  3. Reviewer reads the pull request and leaves PASS or FIX with reasons.
  4. On FIX, the builder fixes on the same branch. Resume the same reviewer seat, not a fresh one.
  5. On PASS, the builder runs npx @0xray/foundry gate, then npx @0xray/foundry gate --verify-only, and merges.
  6. Someone posts the receipt on the ticket: the merged pull request or the live URL.

Green CI alone is not ship. The review PASS and the gate are; see ship gates.

What does the reviewer PASS loop look like in practice?

The reviewer reads the change against the ticket, not against its own taste. A useful verdict names the line, the problem, and what would clear it. "FIX: step 4 says merge before gate; swap them" is a verdict. "Looks off" is not.

Split findings into two kinds. Must-fix items block the merge. Soft items are notes the builder may take or leave, and they never hold the gate. When the builder pushes the fix, it tips the same reviewer seat with a one-line summary of what changed. The reviewer re-checks only the open items, then answers PASS or FIX again.

Two or three rounds is normal on a first ticket. If it hits five, stop and look at the ticket, not the people: the ask is usually too vague or too big. Split it and run the smaller piece.

How do you prove the loop survives a reset?

The house is only real if it survives a context reset. Close the builder's session mid-ticket. Open a new one, on a different host if you have one. The new session should read AGENTS.md, then the station card, then resume the same ticket on the same branch. If it starts over or asks what it was doing, the card is too thin. Fix the card, not the agent.

Run the drill at a real midpoint, after the pull request is open but before review comes back. That is where work most often gets lost. A clean pass looks like this:

  1. The new session names the ticket and branch without being told.
  2. It checks the pull request for review comments before doing anything else.
  3. It picks up the next line from the card, not a guess.
  4. It updates the card when it stops.

Write down how long the resume took and anything it got wrong. Run it again once the card is fixed. A second clean pass is your proof the team can hand work across sessions and hosts.

What spend line should exist before it runs unattended?

Before anything runs unattended, the owner writes down:

  • A weekly compute budget and a hold line where new wakes go quiet.
  • One deep-work cloud run per ticket, after the spec is written.
  • Which actions always need a human yes.

Keep it short enough to paste on the ticket. Name a number, not a feeling, and name who watches it. When the hold line trips, seats finish what they are on, update their cards, and go quiet until the owner raises the line or the week resets. That is a pause, not a failure; the cards mean nothing is lost.

The "human yes" list is usually: spending money, touching credentials, anything public, and merging to main without a PASS. If a seat ever needs one of those, it asks on the ticket and waits.

When does the work go public?

Building and going public are separate lanes. A reviewer PASS on a pull request does not open the public lane. Posts, listings, and outreach wait for the human owner's explicit go.

What does a finished first ticket look like?

  • One ticket closed with a receipt.
  • Each seat has a current station card.
  • A reset resumed work without help.
  • Nobody pasted a key into chat.

What counts as a receipt?

A receipt is a link anyone on the team can open and check without asking: the merged pull request, the commit on main, or the live page returning 200. Post it on the ticket with one line on what shipped. "Done" with no link is not a receipt. If the work isn't checkable from a link, it isn't shipped yet.

What else do operators ask?

What should the first ticket be?

Something small and checkable: one doc page, one test, one config change. Day one proves the loop, not a feature.

Can the builder review its own pull request?

No. Then nobody owns the gate. Keep the reviewer a separate seat and resume it on FIX.

Which host should we use?

Whichever your team already runs. The suit wires OpenCode, Grok, Hermes, OpenClaw, and Cursor the same way.

Build work ships on a recorded review. The public lane stays on hold until the owner gives an explicit go.
