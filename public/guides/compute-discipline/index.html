AI spend control

Govern agent model spend

Yes. Agent compute stays inside a budget when the spec exists before the run, one cloud agent owns the ticket, and new work stops at a weekly hold line. The outcome is a bill that matches finished tickets. You get it by writing the bug, the reproduction, and the paths, then launching only against a ticket id.

Why does agent compute burn the budget?

Cloud agents are easy to fan out and hard to account for. A team launches a run to discover what the task is. Two runs edit one pull request. The weekly bill arrives before the spec does. An empty queue still wakes roles, and the wakes spend more, because nobody set a line where new work stops.

Model spend is an operations problem. It has an owner, a spec, and a ceiling. It is not a side effect of leaving agents on.

How do you govern model spend?

Architecture before the run

Write the bug or the outcome, how to reproduce the current behavior, what finished looks like, and the paths. That page is the spec the run implements. The architecture track sits outside the day-to-day roster. Reach it on the ticket: an issue, a pull request, or a comment that mentions the person who owns the track. A side inbox is a second queue, which the control plane already forbids.

One run on the ticket

Deep work goes to a cloud agent, including a long review. No ticket id, no launch. One implementation run on the ticket, then one review run, and not both live. The run pushes a branch. The role's own application opens the pull request. A wake from the queue does not itself launch a run. Roles do not build the receipt on a laptop. The cloud run is where code and tests execute. A few-line production fix can be deployed by the shipping role once tests are green. Anything larger waits for the cloud run. The release side of that rule is in release gates.

When a second run is allowed

All three have to be true. The current agent already has two or more jobs queued. The new job touches different files. The new job can be briefed from the docs alone. If one is false, the current run keeps the ticket.

The weekly ceiling

Set a weekly budget before the second agent exists. At about three quarters of it, stop waking new work and stop opening a plan for the next wave. Do not launch a run to use the remainder. Essential work already in flight can finish. A hotfix can still ship on green tests. A larger change waits for a run that already exists, or for the budget to reset. Spend, production changes, and publish need the human owner's yes unless the house file names an exception. That house file is written when the team is stood up.

On this fleet the architecture track is Arch1. It writes a fix, or one pipeline (a plate), only when that track is handed over. The spec stays in plain language: the bug, how to reproduce it, what fixed looks like, and the paths. The name is in the glossary.

What do you do before a cloud run?

  1. Write the spec in plain language before you talk about a cloud run. Bug or outcome, reproduction, finished state, paths.
  2. Open the ticket and paste the brief, including acceptance and the ownership line. Launch only against that ticket id.
  3. Keep a single implementation run. When it finishes and the required checks are green, start the review run. Do not leave both live.
  4. Apply the three-part test before any extra run. Two or more jobs already queued, different files, briefable from docs.
  5. Publish the weekly number to the owner and the coordinator. At about three quarters, new wakes and the next-wave plan stay quiet.
  6. Let a few-line production fix ship on green tests. Send everything larger through the cloud run, or wait for the budget.

Where does compute discipline fail?

  • A run launched to invent the spec. The bill pays for exploration. The ticket still has no acceptance line.
  • Two live runs on one pull request. They overwrite each other and the review has no single head to score.
  • A laptop build treated as the receipt. The role's machine is not the plant. The queue never sees a cloud run, and the proof is local.
  • An empty queue that keeps waking roles after the weekly line is already quiet. The wakes spend. They do not create a ticket.
  • Architecture reached on a side channel. The spec never lands on the ticket, so the run implements a conversation.

What else do operators ask?

How do we keep agent compute from burning the budget?

Write the specification before the run. Keep one deep-work run per ticket. Stop opening new runs when weekly spend reaches the hold line. A run with no ticket id does not start.

What does architecture-first mean?

The bug or outcome, the reproduction, what finished looks like, and the paths are written down before a cloud agent is launched. The run implements that spec.

When is a second cloud run justified?

A new run waits until three things are true: the current agent already has two or more jobs queued, the new job touches different files, and the job can be briefed from the docs alone. Otherwise the current run keeps the ticket.

Who is allowed to spend?

Model spend, production changes, and publish sit with the human owner unless the house file names an exception. A role does not invent a budget.

What is the weekly hold line?

When spend reaches about three quarters of the weekly budget, new wakes stay quiet and the next-wave plan stays quiet. Essential work already in flight can finish. A few-line production fix can still ship once tests are green.

Build work ships on a recorded review. The public lane stays on hold until the owner gives an explicit go.
