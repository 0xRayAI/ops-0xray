Agent orchestration

The agent control plane

Yes. Agent orchestration holds when one queue, one owner, and one written procedure still agree after a restart. The outcome is a ticket you can resume, instead of a chat that invented a second plan. You get it by filing a brief before code, waking the next role on that ticket, and rereading the procedure from disk.

What breaks agent orchestration?

Agent orchestration breaks when work has two homes. The ticket says one thing, the chat says another, and after a context reset the role rebuilds a third version from whatever is still in the prompt. Owners overlap. The same bug is fixed twice, or it is not fixed at all.

You cannot operate what you cannot see. A multi-agent system with no queue has no stage, no owner, and no event log. Status becomes a personality trait of the model.

What does the control plane consist of?

The control plane is three objects and one rule.

The queue

One board is the record. When a live URL is configured, each issue, pull request, and comment becomes one ticket and one inbox line for the owning role, and that role is resumed. When the live URL is unset, the hand-kept board in the house folder is the queue. Stages run open, then review, fix, merge, retest, and done. A ticket is live, held, parked, or closed. Work that never becomes a ticket is forgotten as soon as the chat moves on.

The brief

Each ticket carries a short brief: goal, constraints, path, acceptance, gates, evidence, next owner, escalate, and an ownership line. R does the work. A answers for the result. C is consulted before a judgment call. I is informed after the event. Keep each field short enough to re-read on resume, about two hundred characters. A live ticket missing R or A is not ready, and review does not pass it. Acceptance in the brief is the eval the later diff has to meet. Write it before code. That order is what release gates enforce.

The procedure

A pack procedure ships with the kit. The house file overrides it for the owner, the roles, the public voice, what a role may do, what needs a human yes, and which board is real. On every resume, and after every context cut, the role reads that file from disk. A memory note is not the re-read. The stand-up guide shows where the house file points.

The handoff rule

A handoff is the brief delivered to the next role, plus a resume signal that points at the same ticket. The shared room is for talk. The inbox line is the resume. A direct message with no ticket is not work. An advance request only asks the implementer to open or move work the ticket already names. It does not replace the brief.

What you watch

Observability is the queue. Record real events: work opened or pushed, a review verdict, a merge, an owner message, a blocker, a finished deploy. A continuous-integration run is attached to the ticket and is not, by itself, board traffic. A draft parks. A live pull request with no real event for a long stretch parks. An idle loop on parked work is noise.

We call the live queue Bifrost, the brief a packet, the role a seat, and the procedure file OP-PROC. Those names are defined in the glossary.

How do you put the control plane in place?

  1. Declare the queue in the house file. One URL or one file path. Tell every role. Stop updating the other board.
  2. Open a ticket the same day you decide to do the work. One issue or one pull request. Record the owner. Keep the stage honest.
  3. Paste the brief with goal, constraints, path, acceptance, gates, evidence, next owner, escalate, and the ownership line. Fill who does the work and who answers before anyone codes.
  4. Lock the gate list when review starts. The implementer sets it. The reviewer may raise it and does not lower it.
  5. Hand off by delivering the brief and waking the next role on that ticket. Leave the room message as talk. It does not clear the handoff.
  6. On every resume, re-read the procedure from the file the house names, then the session ticket, then the working notes. Continue the intent already written there.

Where does orchestration fail in practice?

  • Two queues. The live board and a hand-kept file both look official. Roles update the one they remember.
  • A task that exists only in chat. There is no owner and no stage, so a restart drops it.
  • A brief with no R or A. The ticket looks busy and review still cannot pass it. The amber mark is the warning, not a pass.
  • A room message treated as the handoff. The next role never gets an inbox line. The ticket sits still while the room looks active.
  • The procedure rewritten from memory after compaction. The house file said something else. The role follows the paraphrase and drifts.

What else do operators ask?

What is the control plane for an agent fleet?

The control plane is the work queue, the ownership on each ticket, and the procedure roles re-read after a restart. Agent orchestration is those three staying in agreement.

Which work queue should we use?

Use one. If the live URL is set, the live board is the queue. If it is unset, the hand-kept house board is the queue. A second board becomes a second memory.

What does a work brief need before anyone starts?

Goal, constraints, path, acceptance, gates, evidence, the next owner, where to escalate, and the ownership line. Who does the work and who answers have to be filled, or the ticket is not ready for a pass.

What resumes a role after context loss?

An inbox line that points at one ticket, plus the session ticket and the procedure on disk. A message in a shared room does not resume the work.

How do we observe the fleet?

Read the queue. Each ticket has an owner, a stage, and a state. Record real events: opened work, a review verdict, a merge, a deploy. A continuous-integration tick is not one of those events.

Build work ships on a recorded review. The public lane stays on hold until the owner gives an explicit go.
