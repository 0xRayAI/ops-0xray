Fleet pitfalls

Common AI agent fleet pitfalls and fixes

Yes. Most agent fleet failures are fixable without a better model. They come from operations: nobody owns the ticket, work stalls silently, spend climbs overnight, or a change ships unreviewed. Write one owner per lane, a station card on disk, a stale check, a spend hold line, and a reviewer PASS gate into your procedure.

Why does an agent forget what it was doing?

Symptom. After a context window closes, the agent asks what it was doing, or redoes finished work.

Fix. The record is on disk. Every seat reads its procedure and station card first, and updates the card before it stops. If you can delete the chat and still resume, you are safe.

Why do two agents work the same ticket?

Symptom. Two agents edit the same file, answer the same message, or undo each other. Tickets bounce between seats.

Fix. One owner per lane, written in the procedure. The coordinator assigns; it does not implement. Agents that are not the owner stay quiet on acknowledgments of known state.

Why it matters. A human sign-off does not make the call human. In Anthropic's study of 50 analysts, experts went with the agent's suggested lean 86% of the time. The MAST failure taxonomy (a catalog of 14 ways multi-agent systems break) lists ignoring the role and ignoring other agents as major failure classes. Public responsibility charts for agents agree: Microsoft's agent Center of Excellence guidance says "Assign exactly one accountable role per task. If two roles are accountable, no one is."

Why does a ticket sit idle with no error?

Symptom. A ticket sits in progress for a day. No error, no message. The agent is waiting on something nobody knows about, often a human step like a login or a key.

Fix. Every ticket has a stage and a state, including blocked and who it is blocked on. The coordinator runs a stale check on a schedule. Blocked-on-human items go into one short checklist for the owner, not scattered across chats.

Give every run three guards: a turn cap (a hard limit on loop steps, like max_turns in the OpenAI Agents SDK), a heartbeat (a periodic "still alive" signal, as in Temporal), and a wake that re-plans when progress stops.

Why does the bill spike overnight?

Symptom. A cloud run loops, retries, or spawns sub-agents until the budget is gone. Or many small wakes add up to a large bill.

Fix. Write the spec before the cloud run. Allow one deep-work run per ticket. Set token ceilings in config. The owner sets a weekly budget and a hold line; past it, new wakes go quiet until reset. Spend and credentials are always ask-first. More in compute discipline.

Why it matters. Anthropic reports that multi-agent systems use about 15 times the tokens of a chat. Without a budget gate, that is a bill, not a fleet.

Here's what it costs in practice. One team reported $47,000 burned when two of four LangChain agents talking agent-to-agent looped on each other for 11 days. As one case-study writeup put it: "The team had observability. They did not have enforcement." Their fixes were plain ones: a daily dollar cap, an iteration limit, and a timeout per call.

Why does a green build still ship a bug?

Symptom. "Tests passed" becomes "shipped." A broken page or a bad config goes live because CI was green.

Fix. Done is a receipt: a reviewer PASS on the pull request plus the release gate, then a live URL or release posted on the ticket. Green CI is the first check, not the ship. Keep the same reviewer seat on a track and resume it. See ship gates.

Also check who can approve. If the person who asked for the work can approve the agent's pull request, there is no review gate. GitHub's Copilot coding agent blocks exactly that.

Why is the same job running twice?

Symptom. A long-running cloud agent seems stuck, so someone starts a fresh one. Now two runs fight over the same branch and both bill.

Fix. One seat owns cloud runs. It resumes the existing run on that track instead of launching a new one. The run ID goes on the station card so any session can find it.

Why did something go public too early?

Symptom. A post, listing, or email goes out before the claim is checked, or with a contact address that bounces.

Fix. Building and going public are separate lanes. A PASS on code does not open the public lane; the human owner's go does. Check every contact path before it ships.

Do you have too many agents?

Symptom. A five-seat fleet for a job one agent and a checklist could do.

Fix. Start simple, then add seats. Anthropic recommends fixed workflows first and agents only for open-ended work, and notes tightly coupled tasks like most coding suit multi-agent setups poorly.

How do you audit your fleet in an hour?

  1. Delete one seat's chat and see if it resumes.
  2. List every ticket in progress and its owner. Any with two owners or none?
  3. Find the oldest idle ticket. Who is it waiting on?
  4. Read last week's spend. Was there a hold line?
  5. Pick three shipped changes. Does each have a review PASS?

If you find more than two gaps, fix the procedure before adding agents. More agents amplify whatever the operations already are.

What else do operators ask?

Which pitfall is most common?

In our practice, chat as the record. It causes most of the others.

Do better models fix these?

No. They are operating problems, and research on multi-agent failures points the same way. A stronger model stalls just as silently without a ticket state.

Is this framework-specific?

No. The fixes apply to any multi-agent stack.

Build work ships on a recorded review. The public lane stays on hold until the owner gives an explicit go.
